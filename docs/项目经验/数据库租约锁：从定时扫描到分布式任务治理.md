# 数据库租约锁：从定时扫描到分布式任务治理

## 1. 背景与目标

在单机项目中，我们很容易写出一个定时扫描任务：

```java
@Scheduled(fixedDelay = 10_000)
public void scan() {
    List<Task> tasks = taskMapper.findDueTasks();
    for (Task task : tasks) {
        executor.execute(() -> process(task));
    }
}
```

这段代码在开发环境里通常运行正常，但部署到生产环境后会立刻遇到几个问题：

1. 应用部署多个实例时，每个实例都会扫描到同一条任务。
2. 扫描线程只负责投递，异步工作线程尚未完成时，下一轮扫描又会看到同一任务。
3. 执行实例宕机后，任务可能永远停留在“处理中”。
4. 锁过期后，旧执行者恢复运行，可能覆盖新执行者的状态。
5. 任务包含文件上传、远程调用、数据库写入等副作用，很难依靠一个本地锁保证一致性。

`ragent` 的知识库文档定时刷新任务使用了数据库租约锁来解决这类问题。本文的重点不是记住某几个类，而是掌握租约锁背后的问题拆解方法，从而能在新的项目中独立设计类似机制。

## 2. 先掌握思想：租约不是永久锁

### 2.1 普通锁关心互斥

普通锁首先回答一个问题：

> 同一时刻是否只有一个执行者进入临界区？

例如 JVM 中的 `synchronized`、`ReentrantLock` 都能解决单进程中的互斥。但是它们无法被其他应用实例看到，因此不能直接用于分布式定时任务。

### 2.2 分布式任务还必须关心存活性

如果只在数据库中记录：

```text
locked = true
```

那么执行者宕机后，没有人会把它改回 `false`，任务将永久锁死。

因此分布式任务不能只问“谁拿到了锁”，还必须问：

> 如果持有者已经死亡，其他执行者什么时候可以接管？

租约锁给锁增加了有效期：

```text
lock_owner = 当前执行者
lock_until = 租约到期时间
```

只要当前时间超过 `lock_until`，其他实例就可以认为旧持有者已经失去执行权并尝试接管任务。

### 2.3 租约锁要同时解决五个问题

设计租约锁时，应当依次回答下面五个问题：

1. **互斥**：多个执行者同时竞争时，怎样保证只有一个成功？
2. **身份**：怎样证明当前写状态或解锁的人仍是原持有者？
3. **存活性**：持有者宕机后，锁怎样自动恢复？
4. **长任务**：任务执行时间超过初始租约时，怎样安全续约？
5. **副作用**：锁丢失后，旧执行者怎样停止写入，避免覆盖新执行者？

这五个问题就是理解和复用租约锁设计的主线。

## 3. 当前项目的调度模型

### 3.1 调度数据

知识库文档调度表为 `t_knowledge_document_schedule`，与调度相关的关键字段如下：

```sql
CREATE TABLE t_knowledge_document_schedule (
    id                VARCHAR(20) PRIMARY KEY,
    doc_id            VARCHAR(20) NOT NULL,
    enabled           SMALLINT DEFAULT 0,
    next_run_time     TIMESTAMP,
    last_run_time     TIMESTAMP,
    last_status       VARCHAR(16),
    last_error        VARCHAR(512),
    lock_owner        VARCHAR(128),
    lock_until        TIMESTAMP
);
```

字段可以分成三组：

| 类别 | 字段 | 作用 |
| --- | --- | --- |
| 调度条件 | `enabled`、`next_run_time` | 判断任务是否应该执行 |
| 执行结果 | `last_run_time`、`last_status`、`last_error` | 记录最近一次结果 |
| 租约状态 | `lock_owner`、`lock_until` | 表示当前执行权和有效期 |

此外，`t_knowledge_document_schedule_exec` 单独保存每次执行记录。主表描述“任务当前状态”，执行表描述“每一次发生过什么”。

### 3.2 scan() 只负责发现和投递

`KnowledgeDocumentScheduleJob#scan()` 默认每 10 秒运行一次，执行三个动作：

1. 查询已经到期并且当前未被锁定的候选任务。
2. 对每个候选任务执行原子抢锁。
3. 抢锁成功后，把任务提交给 `knowledgeChunkExecutor`。

对应逻辑位于：

- `KnowledgeDocumentScheduleJob.java:64-100`
- `bootstrap/src/main/resources/application.yaml:131-136`

扫描 SQL 可以近似理解为：

```sql
SELECT *
FROM t_knowledge_document_schedule
WHERE enabled = 1
  AND (next_run_time IS NULL OR next_run_time <= :now)
  AND (lock_until IS NULL OR lock_until < :now)
ORDER BY next_run_time
LIMIT :batchSize;
```

这里必须建立一个重要认知：

> 查询到任务不等于领取到任务。

多个实例完全可能查询到相同结果。候选查询只负责减少竞争范围，真正的互斥必须由后续原子更新完成。

## 4. 第一层保障：用条件更新原子抢租约

### 4.1 为什么不能先查询再普通更新

错误实现通常是：

```java
Task task = mapper.selectById(id);
if (task.getLockUntil() == null || task.getLockUntil().before(now)) {
    task.setLockOwner(myToken);
    mapper.updateById(task);
}
```

实例 A 和实例 B 可以同时读到“未加锁”，然后先后执行普通更新，最终两边都会认为自己成功。

这是典型的检查与使用之间竞争，也就是 TOCTOU（Time Of Check To Time Of Use）。

### 4.2 正确做法是把判断放进 UPDATE

当前项目的 `ScheduleLockManager#tryAcquire()` 把“锁是否可用”和“设置新租约”放在同一条 SQL 中：

```sql
UPDATE t_knowledge_document_schedule
SET lock_owner = :newToken,
    lock_until = :newLockUntil
WHERE id = :scheduleId
  AND (lock_until IS NULL OR lock_until < :now);
```

然后根据影响行数判断结果：

```java
return updated > 0 ? lease : null;
```

数据库会对这条更新进行并发控制。两个实例同时竞争同一行时，只有一个实例能满足条件并成功更新，另一个实例最终得到 0 行。

这里使用了数据库的短事务和短暂行锁，但业务任务运行期间不会一直持有数据库行锁。任务执行权由表中的租约状态表达。

### 4.3 可迁移原则

在新项目中设计任务领取时，牢记下面这条规则：

> 领取条件和领取动作必须在同一个原子操作里完成。

数据库方案通常使用条件 `UPDATE`、`UPDATE ... RETURNING` 或 `SELECT ... FOR UPDATE SKIP LOCKED`；Redis 方案通常使用 Lua 脚本或带条件的原子命令。

## 5. 第二层保障：每次领取生成唯一身份

### 5.1 为什么 scheduleId 不能代表持有者

假设发生以下过程：

1. 实例 A 获得任务 100 的租约。
2. A 因网络或长时间 GC 暂停，租约过期。
3. 实例 B 接管任务 100。
4. A 恢复并执行释放锁。

如果释放条件只有 `WHERE id = 100`，A 会错误地释放 B 的锁。

因此，每次领取都需要一个不可重复的执行身份：

```text
scheduleId = 100
lockToken  = kb-schedule-host-instanceUUID:executionUUID
```

项目中的身份对象是：

```java
public record ScheduleLockLease(String scheduleId, String lockToken) {
}
```

### 5.2 所有敏感操作都必须校验身份

释放租约：

```sql
UPDATE t_knowledge_document_schedule
SET lock_owner = NULL,
    lock_until = NULL
WHERE id = :scheduleId
  AND lock_owner = :myToken;
```

续约：

```sql
UPDATE t_knowledge_document_schedule
SET lock_until = :newLockUntil
WHERE id = :scheduleId
  AND lock_owner = :myToken;
```

写回调度结果：

```sql
UPDATE t_knowledge_document_schedule
SET next_run_time = :nextRunTime,
    last_status = :status
WHERE id = :scheduleId
  AND lock_owner = :myToken;
```

这三类操作都遵守同一个原则：

> 我曾经拥有锁，不代表我现在仍拥有锁；每次关键写操作都要重新证明身份。

对应代码：

- `ScheduleLockManager.java:70-93`
- `ScheduleStateManager.java:206-214`

### 5.3 token 与 fencing token 的区别

当前项目使用随机 UUID 作为所有权 token，它能防止旧执行者修改调度主表，但它不是严格意义上的 fencing token。

严格 fencing token 一般是单调递增版本号，例如：

```text
第一次领取：version = 41
第二次领取：version = 42
```

下游存储只接受更大的版本号，因此版本 41 的旧请求即使晚到，也会被拒绝。

当前项目的文件存储、文档分块和向量索引并不识别 `lockToken`，所以随机 token 只能保护带有 `lock_owner` 条件的数据库更新，不能自动隔离所有外部副作用。

在新项目中应明确区分：

- ownership token：证明当前是否仍持有某条任务。
- fencing token：让下游系统拒绝过期执行者的写入。

## 6. 第三层保障：TTL 解决宕机后的接管

### 6.1 为什么锁必须过期

如果持有者在任务中途进程退出，它不会执行 `finally`，也不会调用 `release()`。因此解锁不能只依赖主动释放。

项目在领取时写入：

```text
lock_until = 当前时间 + lockSeconds
```

默认 `lockSeconds = 900`，即 15 分钟。超过该时间后，其他实例可以重新领取。

这种设计把永久死锁转化为最多等待一个 TTL 的可恢复故障。

### 6.2 TTL 的取值不是越短越好

TTL 太长：

- 宕机后恢复慢。
- 故障任务长时间不能被其他实例接管。

TTL 太短：

- 短暂网络波动或 JVM 停顿就可能导致租约过期。
- 心跳频率必须提高，数据库写压力增大。
- 长任务更容易在正常执行期间被误判为失效。

实践中可以先估算：

```text
TTL > 最大可接受的网络抖动 + 最大 GC 停顿 + 心跳调度延迟
```

任务真实耗时可以远大于 TTL，但前提是存在稳定续约机制。

## 7. 第四层保障：心跳让长任务持续持有租约

### 7.1 心跳机制

`ScheduleLockManager#startHeartbeat()` 为每个运行中的任务创建定时续约：

```java
heartbeatExecutor.scheduleWithFixedDelay(
        () -> doHeartbeat(heartbeat),
        intervalMillis,
        intervalMillis,
        TimeUnit.MILLISECONDS
);
```

续约间隔计算规则为：

```text
max(5 秒, min(TTL / 3, 60 秒))
```

默认 TTL 为 900 秒，所以默认每 60 秒续约一次。

### 7.2 为什么任务启动时还要主动续约

`scan()` 抢到锁后只是把任务提交到线程池。线程池配置了有界队列：

```java
new LinkedBlockingQueue<>(200)
```

如果线程池繁忙，任务可能长时间排队。心跳是在工作线程真正进入 `process()` 后才启动，因此处理器第一步会主动执行一次 `renew()`，确认排队期间租约没有丢失。

如果续约失败，任务直接放弃执行，不能继续相信扫描阶段拿到的旧租约。

对应代码：

- `ScheduleRefreshProcessor.java:66-90`
- `rag/src/main/java/com/nageoffer/ai/ragent/rag/config/ThreadPoolExecutorConfig.java:197-214`

### 7.3 心跳异常要区分短暂失败和确认失效

当前项目记录最近一次成功续约时间：

```text
lastConfirmedAt
```

当数据库临时不可用时，不会因一次异常立刻宣布锁丢失；只有从最近一次确认开始已经超过完整 TTL，才标记租约失效。

这里体现了一个重要思想：

> “续约请求失败”不一定等于“租约已经失效”，但超过安全窗口仍无法确认时，必须按失效处理。

## 8. 第五层保障：业务资源还要有自己的并发门闩

### 8.1 调度锁和文档运行权不是一回事

调度租约保护的是同一条 `scheduleId`，但同一文档还可能被用户手动触发分块。因此项目对文档状态执行第二次 CAS：

```sql
UPDATE t_knowledge_document
SET status = 'RUNNING',
    update_time = :now
WHERE id = :docId
  AND deleted = 0
  AND enabled = 1
  AND status <> 'RUNNING';
```

影响 1 行表示成功领取文档运行权；影响 0 行表示文档已经被其他流程占用。

对应代码为 `DocumentStatusHelper.java:42-54`。

### 8.2 两层锁解决不同问题

| 保护层 | 保护对象 | 防止的并发 |
| --- | --- | --- |
| 调度租约 | `scheduleId` | 多实例扫描、重复调度 |
| 文档状态 CAS | `docId` | 定时刷新与手动分块并发 |

在新项目中，不要认为有了调度锁就能自动保护所有业务资源。应该继续追问：

> 是否还有其他入口能够修改同一个业务对象？

如果存在，就需要业务对象自己的状态机、版本号、唯一约束或幂等机制。

## 9. 以文档扫描任务推演完整流程

### 9.1 正常执行

假设一个 URL 文档下一次执行时间为 `10:00:00`，Cron 每 5 分钟执行一次。

1. `10:00:03`，实例 A 和 B 都执行 `scan()`。
2. A、B 都查询到这条候选记录。
3. A 的条件更新影响 1 行，获得 `token-A`。
4. B 的条件更新影响 0 行，跳过任务。
5. A 将任务提交给 `knowledgeChunkExecutor`。
6. 工作线程启动后主动续约，确认 `token-A` 仍有效。
7. 启动心跳线程，周期性延长 `lock_until`。
8. 重新查询最新调度记录和文档配置，不能完全依赖扫描快照。
9. 根据当前 Cron 和任务开始时间计算 `next_run_time = 10:05:00`。
10. 插入一条状态为 `RUNNING` 的执行记录。
11. 根据旧 ETag、Last-Modified 和内容哈希拉取远程文件。
12. 如果内容未变化，写回 `SKIPPED` 和新的 `next_run_time`。
13. 如果内容变化，CAS 抢占文档运行权，上传文件并执行分块。
14. 分块成功后切换文档文件元数据。
15. 使用 `WHERE lock_owner = token-A` 写回 `SUCCESS`、内容摘要和下一次时间。
16. 关闭心跳。
17. 使用 `WHERE lock_owner = token-A` 释放租约。

### 9.2 线程池拒绝

线程池使用有界队列和 `AbortPolicy`。如果任务无法提交，会抛出 `RejectedExecutionException`。

此时任务还没有开始执行，但扫描线程已经获得租约，所以必须立即释放：

```java
try {
    executor.execute(task);
} catch (RejectedExecutionException e) {
    lockManager.release(lease);
}
```

否则任务只能等待 TTL 到期才能再次被扫描，造成不必要的延迟。

### 9.3 执行实例宕机

假设 A 抢到任务并开始分块，随后进程退出：

1. A 无法执行 `finally`，所以不会主动释放租约。
2. A 的心跳随进程停止。
3. `lock_until` 到期后，B 可以接管调度任务。
4. 文档可能仍停留在 `RUNNING`。
5. `recoverStuckRunningDocuments()` 每 60 秒扫描长时间处于 `RUNNING` 的文档。
6. 超过安全阈值后，文档状态被重置为 `FAILED`，允许后续重试。

这里能看到两套恢复机制：

- 调度租约 TTL 恢复调度执行权。
- 文档运行超时恢复业务对象状态。

### 9.4 锁在执行中被其他实例接管

假设 A 因长时间暂停错过续约，B 在租约过期后成功接管：

1. B 抢锁时把 `lock_owner` 改成 `token-B`。
2. A 恢复后执行续约，因 token 不匹配而影响 0 行。
3. A 的心跳将租约标记为 `lost`。
4. A 在关键阶段调用 `shouldAbortForLeaseLoss()` 时停止继续执行。
5. A 写调度状态时也因 token 不匹配而失败。
6. A 最后的释放操作不会删除 B 的租约。

这就是所有权 token 的核心价值：旧执行者可以恢复，但不能继续冒充当前持有者。

## 10. 状态机比 try-finally 更重要

任务包含多个不可同时回滚的动作：

1. 拉取临时文件。
2. 上传新文件。
3. 执行文档分块和向量替换。
4. 切换文档文件元数据。
5. 更新调度状态。
6. 删除旧文件。

这些动作横跨数据库、文件存储和向量索引，无法依赖一个本地数据库事务整体回滚。因此 `ScheduleRefreshProcessor` 使用阶段状态记录执行进度：

```text
INIT
DOC_OCCUPIED
CHUNK_STARTED
CHUNK_COMPLETED
FILE_SWITCHED
```

清理逻辑根据阶段决定：

- 新文件已上传但尚未完成分块：删除新文件。
- 分块完成但文件元数据尚未切换：保留新文件，避免删除已经被索引引用的资源。
- 文件已经切换：删除旧文件。
- 锁丢失且文档仍为 `RUNNING`：尝试标记失败。

可以提炼出一个更通用的经验：

> 租约锁解决谁有权执行，状态机解决执行到一半时系统处于什么状态、应该如何补偿。

复杂任务不能只写一个大 `try-finally`，还需要显式描述阶段、可重试点和补偿策略。

## 11. 这套设计提供什么一致性语义

### 11.1 它不是 exactly-once

数据库租约只能尽量避免并发执行，无法保证任务严格只执行一次。以下情况都可能造成重复尝试：

- 成功完成外部副作用后，写回数据库前进程宕机。
- 锁在长操作期间失效，但旧调用已经发送到外部系统。
- 网络超时导致调用方不知道下游是否已经成功。
- 候选查询和真正领取之间发生状态变化。

因此更准确的语义是：

```text
at-least-once 调度 + 所有权校验 + 业务幂等/补偿
```

### 11.2 设计目标应当是重复执行也可控

新项目中不要把全部希望寄托在“绝不重复执行”上，而应同时设计：

- 幂等键，例如 `taskId + executionVersion`。
- 唯一约束，避免重复插入业务结果。
- 状态 CAS，避免非法状态跳转。
- replace/upsert 语义，避免重复追加。
- 执行记录，支持审计和人工排查。
- 补偿任务，处理跨系统部分成功。

## 12. 当前实现值得学习的地方

### 12.1 候选发现和任务领取分离

查询用于提高扫描效率，条件更新用于保证领取互斥，职责清晰。

### 12.2 锁有 TTL，不依赖正常退出

即使进程无法执行 `finally`，任务也不会永久锁死。

### 12.3 每次执行使用独立 token

旧执行者不能释放新执行者的锁，也不能覆盖新执行者的调度状态。

### 12.4 长任务有自动心跳，也有关键阶段主动确认

后台心跳负责持续续租，关键副作用之前主动续约负责降低竞态风险。

### 12.5 调度状态写回也受租约保护

锁不只保护“开始执行”，还保护最终状态，避免旧执行者回写过时结果。

### 12.6 调度锁和业务状态 CAS 分层

它认识到任务入口不只有定时扫描，因此对文档本身增加了独立运行权控制。

### 12.7 有界线程池拒绝后立即释放

领取成功不等于任务一定能进入工作线程；投递失败也是必须设计的异常分支。

## 13. 当前实现的边界与改进方向

### 13.1 抢锁时没有重新校验任务是否仍然到期

当前候选查询检查了：

```text
enabled = 1
next_run_time <= now
lock 已过期
```

但 `tryAcquire()` 只重新检查了锁是否过期。

可能出现：

1. A 和 B 同时查询到任务。
2. A 抢锁、快速完成、更新 `next_run_time` 并释放。
3. B 随后才执行 `tryAcquire()`。
4. B 发现锁为空，于是领取成功，尽管任务已不再到期。

通常第二次远程拉取会因 ETag 或哈希没有变化而变成 `SKIPPED`，但仍产生额外请求和执行记录。

更完整的领取 SQL 应当重新包含全部领取条件：

```sql
UPDATE t_knowledge_document_schedule
SET lock_owner = :token,
    lock_until = :lockUntil
WHERE id = :id
  AND enabled = 1
  AND (next_run_time IS NULL OR next_run_time <= :now)
  AND (lock_until IS NULL OR lock_until < :now);
```

通用原则是：

> 候选查询中的业务前置条件，只要可能在领取前变化，就应在原子领取操作中再次校验。

### 13.2 使用 JVM 时间会受到多节点时钟偏差影响

当前 `now` 和 `lockUntil` 都由应用实例计算。如果实例 A 的时间快、实例 B 的时间慢，可能影响任务到期和租约过期判断。

可选改进：

- 所有节点启用可靠的 NTP 时间同步。
- 使用数据库 `CURRENT_TIMESTAMP` 统一时间来源。
- 在 SQL 中计算 `lock_until = CURRENT_TIMESTAMP + INTERVAL ...`。

数据库时间方案更统一，但会增加 SQL 方言差异，需要结合数据库类型选择。

### 13.3 token 不能隔离外部系统的旧请求

调度主表更新校验了 token，但文件存储和向量索引没有校验 token。锁如果在耗时的 `chunkDocument()` 中途丢失，已经发出的外部写入无法被自动撤销。

可能的加强方式：

- 下游支持单调递增 fencing version。
- 索引写入使用按文档整体 replace 的幂等语义。
- 为每次构建创建新版本，完成后通过一次 CAS 切换 active version。
- 旧版本异步回收，不直接覆盖当前版本。

### 13.4 领取发生在线程池排队之前

任务可能拿到 15 分钟租约后在队列中等待。虽然处理器启动时会重新续约确认，但排队期间会占用租约，并可能降低任务吞吐。

可根据项目负载选择：

- 保持当前方案，但让 TTL 大于正常最大排队时间。
- 控制每轮领取数量，使其接近线程池可用容量。
- 在线程池入口执行领取，而不是扫描线程提前领取。
- 引入独立任务队列，由消费者按自身容量拉取。

### 13.5 单线程心跳执行器需要容量评估

当前所有任务的心跳共用一个单线程 `ScheduledExecutorService`。数据库更新很快时足够简单可靠，但并发任务数量很大或数据库延迟升高时，心跳可能排队。

需要监控：

- 活跃租约数量。
- 心跳执行耗时和延迟。
- 续约失败次数。
- 距离 `lock_until` 的剩余安全时间。

### 13.6 主状态与执行记录不是同一个事务

`ScheduleStateManager` 先更新调度主表，再更新执行记录，两次更新没有统一事务。数据库瞬时异常可能造成：

- 主表成功，执行记录仍为 `RUNNING`。
- 主表更新失败，执行记录带锁失效说明结束。

当前代码通过执行记录消息和异常分支提供了一定可观测性。新项目需要根据一致性要求决定：

- 同库写入是否放在本地事务中。
- 是否允许执行记录最终一致。
- 是否增加后台修复长期 `RUNNING` 执行记录的任务。

### 13.7 RUNNING 恢复阈值必须大于合法最长耗时

项目会把长时间处于 `RUNNING` 的文档重置为 `FAILED`，最小阈值为 10 分钟。若一次合法分块可能超过阈值，恢复任务就可能误判活跃任务。

更稳妥的设计可以让业务状态也带心跳时间，恢复任务判断“最近心跳”而不是只判断“开始时间”。

## 14. 在新项目中落地的推荐步骤

### 第一步：先定义任务状态和执行语义

至少明确：

- 哪个字段表示任务到期。
- 成功、失败、跳过后怎样计算下一次时间。
- 任务允许至少一次还是必须尽量一次。
- 重复执行是否会破坏数据。
- 哪些动作可重试，哪些动作需要补偿。

不要先写锁，再补业务状态。锁应服务于明确的任务状态机。

### 第二步：设计任务表和执行表

一个通用任务表可以包含：

```sql
CREATE TABLE scheduled_task (
    id              BIGINT PRIMARY KEY,
    task_type       VARCHAR(64) NOT NULL,
    payload         JSON,
    enabled         BOOLEAN NOT NULL,
    next_run_at     TIMESTAMP,
    last_status     VARCHAR(32),
    last_error      VARCHAR(1000),
    lease_owner     VARCHAR(128),
    lease_until     TIMESTAMP,
    execution_no    BIGINT NOT NULL DEFAULT 0,
    updated_at      TIMESTAMP NOT NULL
);
```

执行表记录每一次尝试：

```sql
CREATE TABLE task_execution (
    id              BIGINT PRIMARY KEY,
    task_id         BIGINT NOT NULL,
    execution_no    BIGINT NOT NULL,
    status          VARCHAR(32) NOT NULL,
    started_at      TIMESTAMP,
    finished_at     TIMESTAMP,
    worker          VARCHAR(128),
    message         VARCHAR(1000),
    UNIQUE (task_id, execution_no)
);
```

`execution_no` 可以同时承担单调版本号和执行批次号的职责。

### 第三步：实现完整条件的原子领取

推荐的数据库领取语义：

```sql
UPDATE scheduled_task
SET lease_owner = :token,
    lease_until = CURRENT_TIMESTAMP + :ttl,
    execution_no = execution_no + 1
WHERE id = :id
  AND enabled = TRUE
  AND next_run_at <= CURRENT_TIMESTAMP
  AND (lease_until IS NULL OR lease_until < CURRENT_TIMESTAMP)
RETURNING id, execution_no;
```

需要保证：

- 业务到期条件在领取时重新校验。
- 租约条件和写租约在同一条语句中。
- 领取方只能通过影响行数或 `RETURNING` 结果判断成功。
- 不能因为候选查询返回了任务就默认自己拥有它。

### 第四步：生成可追踪的所有权 token

token 至少应包含：

```text
应用名 + 实例标识 + 启动批次 + 每次执行 UUID
```

日志必须始终同时输出：

```text
taskId、leaseOwner、executionNo、stage
```

这样才能在多实例日志中还原接管过程。

### 第五步：实现续约、释放和带所有权的状态更新

三个操作必须全部校验当前 token：

```text
renew(taskId, token)
release(taskId, token)
finishIfOwned(taskId, token, result)
```

其中 `finishIfOwned` 非常重要。只保护领取和释放，不保护结果写回，仍然可能被恢复运行的旧执行者覆盖。

### 第六步：在关键副作用前重新确认租约

建议在这些节点调用 `ensureLeaseOwned()`：

- 工作线程真正启动时。
- 发起不可逆远程调用前。
- 切换业务主版本前。
- 写最终成功状态前。

但不要误以为检查之后就永远安全。检查与副作用之间仍可能丢锁，所以副作用本身最好具备幂等性或 fencing 能力。

### 第七步：显式记录阶段和补偿动作

为长任务建立阶段枚举，例如：

```text
CLAIMED
INPUT_READY
PROCESSING
OUTPUT_WRITTEN
ACTIVATED
COMPLETED
```

对每个阶段回答：

- 进程此时宕机会留下什么？
- 重试是否安全？
- 哪些临时资源需要删除？
- 哪些结果必须保留？
- 谁负责后台补偿？

### 第八步：补齐监控和恢复任务

至少监控：

- 每轮扫描候选数、领取成功数、竞争失败数。
- 线程池活跃数、队列长度、拒绝次数。
- 租约续约成功率、续约延迟、锁丢失次数。
- 各状态任务数量及最长停留时间。
- 从计划时间到实际开始时间的调度延迟。
- 重复执行次数和幂等冲突次数。

恢复任务至少处理：

- 长时间 `RUNNING` 但没有心跳的业务对象。
- 长时间未结束的执行记录。
- 未清理的临时文件或中间版本。

## 15. 方案选择：什么时候用数据库租约锁

### 15.1 适合使用数据库租约锁

- 任务量中小，扫描频率不高。
- 调度数据本来就在关系数据库中。
- 希望少引入一个 Redis、MQ 或专业调度平台。
- 任务需要与数据库业务状态紧密结合。
- 能接受至少一次执行，并能够做幂等或补偿。

### 15.2 考虑 SELECT FOR UPDATE SKIP LOCKED

当需要一次领取多条任务，并希望数据库直接跳过其他消费者正在处理的行时，可以使用：

```sql
SELECT ...
FOR UPDATE SKIP LOCKED
LIMIT :batchSize;
```

它适合数据库任务队列，但要注意事务边界：通常只在短事务中完成“选取并标记已领取”，不能在整个业务任务期间持有事务。

### 15.3 考虑 Redis 租约锁

适用于：

- 锁竞争频率高。
- 锁状态不需要和业务数据库联合查询。
- 团队已经具备成熟 Redis 运维和客户端封装。

仍然必须考虑 token、TTL、续约、误删他人锁和外部副作用，换成 Redis 并不会让这些问题消失。

### 15.4 考虑消息队列或调度平台

当任务量大、需要削峰、重试、死信、优先级、消费组或复杂调度时，应该考虑：

- RocketMQ、Kafka、RabbitMQ 等消息队列。
- XXL-JOB、Quartz 集群模式等调度系统。
- 基于数据库 outbox 的可靠事件投递。

专业组件能解决任务分发问题，但业务幂等、状态机和跨系统副作用仍然需要业务代码设计。

## 16. 故障场景检查表

设计完成后，可以用下面的问题逐项推演：

| 场景 | 必须回答的问题 |
| --- | --- |
| 两个实例同时扫描 | 是否只有一个条件更新成功？ |
| 扫描后任务状态改变 | 领取时是否重新检查全部业务条件？ |
| 线程池已满 | 是否立即释放已获得的租约？ |
| 任务排队超过 TTL | 启动时是否重新确认所有权？ |
| 执行者宕机 | TTL 到期后能否被接管？ |
| 数据库短暂不可用 | 一次心跳失败是否会误判？ |
| 旧执行者恢复 | 是否无法续约、写状态和释放新锁？ |
| 锁在远程调用中失效 | 下游写入是否幂等或带 fencing？ |
| 成功后写状态失败 | 下次重试是否会破坏已有结果？ |
| 主表成功、执行表失败 | 是否允许不一致，怎样修复？ |
| 任务长期 RUNNING | 是否有可靠的心跳或恢复依据？ |
| 多节点时钟偏差 | 时间来源是否统一？ |

如果这些问题没有答案，说明实现可能只有“抢锁代码”，还没有形成完整的分布式任务治理方案。

## 17. 最终应掌握的思考框架

面对一个新的定时扫描任务，不要直接问“用 Redis 锁还是数据库锁”，而应按以下顺序思考：

1. **任务如何被发现**：谁扫描，扫描条件是什么？
2. **任务如何被原子领取**：竞争者怎样得到唯一结果？
3. **执行权如何证明**：旧执行者怎样被识别和拒绝？
4. **持有者死亡如何恢复**：TTL 和恢复延迟是多少？
5. **长任务如何续命**：心跳频率、安全窗口和容量如何设计？
6. **业务资源如何互斥**：是否还有手动入口或其他任务入口？
7. **副作用如何幂等**：重复执行、超时未知和部分成功怎样处理？
8. **过程如何观测**：执行记录、token、阶段和指标是否完整？
9. **失败如何补偿**：临时资源、卡死状态和不一致记录由谁修复？

租约锁并不是一个单独的工具类，而是一套围绕“执行权会过期”建立的协作协议。真正值得迁移到新项目的，不是 `lock_owner` 和 `lock_until` 两个字段本身，而是下面这组完整思想：

```text
原子领取
+ 唯一所有权身份
+ 可过期租约
+ 心跳续约
+ 带所有权的状态写回
+ 业务幂等
+ 阶段化补偿
+ 可观测与恢复
```

只有这些能力形成闭环，数据库租约锁才能从“避免重复执行的小技巧”升级为可在生产环境中使用的分布式任务治理方案。
