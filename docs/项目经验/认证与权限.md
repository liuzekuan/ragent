# 认证与权限

## 背景

当前仓库已经在根 `pom.xml` 中统一管理 `Sa-Token 1.45.0`、`sa-token-spring-boot4-starter` 与 `sa-token-redis-template`，并且项目基线是 `Spring Boot 4.1.0`，说明这里的认证体系不是临时接入，而是平台级能力的一部分。相关代码见：`pom.xml:17-25`、`pom.xml:121-130`。

本文只引用三类一手资料：

1. Sa-Token 官方文档
2. Sa-Token 官方 GitHub 仓库/源码
3. 当前仓库代码

目标是把 Sa-Token 的官方能力，与本仓库实际登录、鉴权、角色校验和 `UserContext` 用法对齐。

## 现象

### 1. Sa-Token 是什么，由谁维护

- Sa-Token 官方仓库将自己定位为“开源、免费、一站式 Java 权限认证框架”，能力覆盖登录认证、权限认证、分布式 Session、微服务网关鉴权、SSO 单点登录、OAuth2.0、JWT、API Key 与 API 参数签名。[官方仓库](https://github.com/dromara/Sa-Token) [官方 README](https://github.com/dromara/Sa-Token/blob/dev/README.md)
- 官方仓库归属 `dromara/Sa-Token`，因此可以确认 Sa-Token 由 Dromara 开源社区维护。[仓库首页](https://github.com/dromara/Sa-Token)

### 2. 核心特性与适用场景

#### 2.1 核心特性

- 登录认证：`StpUtil.login(...)`、`StpUtil.logout()`、`StpUtil.checkLogin()`、`StpUtil.isLogin()`、`StpUtil.getLoginIdAsString()` 等是官方标准入口。[StpUtil 官方 API](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/api/stp-util.md)
- 角色与权限认证：官方提供 `checkRole(...)`、`checkPermission(...)`、`hasRole(...)`、`hasPermission(...)` 等能力，并通过 `StpInterface` 让业务系统决定角色/权限的实际来源。[StpUtil 官方 API](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/api/stp-util.md) [权限扩展文档](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/use/jur-auth.md)
- 路由拦截：官方推荐通过 `SaInterceptor` 接入 Spring MVC，并可在拦截器里配合 `SaRouter.match(...).check(...)` 做分路径鉴权。[路由鉴权文档](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/use/route-check.md)
- 扩展场景：官方 README 明确覆盖 SSO、OAuth2.0、微服务网关鉴权、JWT、API Key 等场景。[官方 README](https://github.com/dromara/Sa-Token/blob/dev/README.md)

#### 2.2 适用场景

- 传统后台系统或前后端分离系统，需要快速建立登录态、会话与角色校验。[StpUtil 官方 API](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/api/stp-util.md)
- Spring Boot / Spring MVC 项目，需要统一地在拦截器层做“默认登录、少数接口放行”的全局控制。[路由鉴权文档](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/use/route-check.md)
- 希望把用户、角色、权限的加载逻辑留在自己业务代码里，而不是交给黑盒中间件。[权限扩展文档](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/use/jur-auth.md)

### 3. 在新的 Java / Spring Boot 平台从零接入的方法

#### 3.1 选择正确的 Starter

官方文档明确区分 Spring Boot 版本：

- Spring Boot 3.x 使用 `sa-token-spring-boot3-starter`
- Spring Boot 4.x 使用 `sa-token-spring-boot4-starter`

来源见：[接入示例文档](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/start/example.md)

如果需要把 Token / Session 放到 Redis，官方 Boot 4 Redis 示例使用的是：

```xml
<dependency>
    <groupId>cn.dev33</groupId>
    <artifactId>sa-token-spring-boot4-starter</artifactId>
    <version>${sa-token.version}</version>
</dependency>

<dependency>
    <groupId>cn.dev33</groupId>
    <artifactId>sa-token-redis-template</artifactId>
    <version>${sa-token.version}</version>
</dependency>
```

来源见：[Spring Boot 4 + Redis 官方示例](https://github.com/dromara/Sa-Token/blob/dev/sa-token-demo/sa-token-demo-springboot4-redis/pom.xml)

#### 3.2 增加基础配置

官方示例给出的 `sa-token` 核心配置包括：`token-name`、`timeout`、`active-timeout`、`is-concurrent`、`is-share`、`token-style`、`is-log` 等。[官方配置示例](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/start/example.md)

当前仓库实际配置为：

- `token-name: Authorization`
- `timeout: 2592000`
- `is-concurrent: true`
- `is-share: false`
- `token-style: simple-uuid`
- `is-log: false`
- `is-print: false`

相关代码见：`bootstrap/src/main/resources/application.yaml:315-322`。

这意味着本仓库把 Sa-Token 的 token 名称直接收敛成 HTTP 头 `Authorization`，而不是默认的 `satoken`。

#### 3.3 实现登录、登出与登录态判断

官方标准做法是：

- 认证通过后调用 `StpUtil.login(loginId)` 建立登录态
- 调用 `StpUtil.logout()` 注销
- 用 `StpUtil.isLogin()` 做无异常判断
- 用 `StpUtil.checkLogin()` 做强制鉴权，未登录时抛 `NotLoginException`
- 用 `StpUtil.getLoginIdAsString()` 读取当前登录账号 id

来源见：[StpUtil 官方 API](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/api/stp-util.md) [登录示例](https://github.com/dromara/Sa-Token/blob/dev/sa-token-demo/sa-token-demo-case/src/main/java/com/pj/cases/use/LoginAuthController.java)

如果前端自己托管 token，还可以通过 `StpUtil.getTokenValue()` 把 token 返回给前端。[StpUtil 官方 API](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/api/stp-util.md)

#### 3.4 注册全局拦截器

官方推荐在 `WebMvcConfigurer` 中注册 `SaInterceptor`，用 `StpUtil.checkLogin()` 或 `SaRouter.match(...).check(...)` 描述规则。[路由鉴权文档](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/use/route-check.md)

#### 3.5 在业务代码里调用角色 / 权限 API

官方已经把常用 API 收敛得很清楚：

- 登录校验：`checkLogin()` / `isLogin()`
- 角色校验：`checkRole(...)`
- 权限校验：`checkPermission(...)`
- 当前账号：`getLoginIdAsString()`

来源见：[StpUtil 官方 API](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/api/stp-util.md)

### 4. 结合本仓库的登录 / 鉴权 / 角色校验流程与 API 用法

#### 4.1 登录与登出

本仓库后端登录入口是：

- `POST /auth/login`
- `POST /auth/logout`

接口定义见：`bootstrap/src/main/java/com/nageoffer/ai/ragent/user/controller/AuthController.java:43-55`。

实际登录逻辑在 `AuthServiceImpl`：

1. 校验用户名、密码非空
2. 按用户名查库
3. 直接比较输入密码与库中密码
4. 取用户 id 作为 `loginId`
5. 调用 `StpUtil.login(loginId)`
6. 用 `StpUtil.getTokenValue()` 把 token 放进 `LoginVO`

相关代码见：`bootstrap/src/main/java/com/nageoffer/ai/ragent/user/service/impl/AuthServiceImpl.java:41-63`。

这说明本仓库采用的是“后端返回 token，前端自己保存”的前后端分离模式，而不是完全依赖 Cookie 自动会话。

#### 4.2 前端 token 传递方式

前端侧调用关系是：

- `frontend/src/services/authService.ts:7-16` 负责请求 `/auth/login`、`/auth/logout`、`/user/me`
- `frontend/src/stores/authStore.ts:24-114` 负责登录后保存 token、设置当前用户、退出登录时清空状态
- `frontend/src/utils/storage.ts:3-59` 把 token 与用户信息放到 `localStorage`
- `frontend/src/services/api.ts:13-25` 在 Axios 默认头和请求拦截器中注入 `Authorization`
- `frontend/src/stores/chatStore.ts:470-475` 在流式聊天请求里也手动补充 `Authorization`

这里有两个实现细节需要特别记住：

1. 前端发送的是原始 token 值，不是 `Bearer <token>` 形式。
2. 这个约定成立的前提，是后端把 `sa-token.token-name` 设成了 `Authorization`。

如果后续要切回默认 `satoken` 名称，或者切换到 `Bearer` 语义，就必须同时改后端配置、Axios 注入逻辑和流式请求逻辑。

#### 4.3 全局登录校验链路

本仓库通过 `SaInterceptor` 做全局登录检查：

- 拦截所有路径 `/**`
- 放行 `/auth/**` 与 `/error`
- 对 `ASYNC` 调度请求与 `OPTIONS` 预检请求跳过登录检查
- 其余请求统一执行 `StpUtil.checkLogin()`

相关代码见：`bootstrap/src/main/java/com/nageoffer/ai/ragent/user/config/SaTokenConfig.java:45-89`。

`UserContextInterceptor` 负责在登录检查通过后，把当前登录用户转成业务快照：

- 调用 `StpUtil.getLoginIdAsString()`
- 再按 `loginId` 查 `UserDO`
- 把 `userId / username / role / avatar` 封装成 `LoginUser`
- 放进 `TransmittableThreadLocal` 支持的 `UserContext`
- 请求结束后清理上下文

相关代码见：`bootstrap/src/main/java/com/nageoffer/ai/ragent/user/config/UserContextInterceptor.java:61-89`、`framework/src/main/java/com/nageoffer/ai/ragent/framework/context/LoginUser.java:25-53`、`framework/src/main/java/com/nageoffer/ai/ragent/framework/context/UserContext.java:24-99`。

因此可以把两者的关系概括为：

- Sa-Token 负责“当前请求到底有没有登录、登录账号是谁”
- `UserContext` 负责“把当前登录账号转换成业务可直接消费的用户快照”

`/user/me` 就是这个设计的最直接例子：接口并不直接读 `StpUtil`，而是通过 `UserContext.requireUser()` 返回当前用户视图对象。相关代码见：`bootstrap/src/main/java/com/nageoffer/ai/ragent/user/controller/UserController.java:55-64`。

#### 4.4 角色校验与权限来源

本仓库当前真正使用的是“角色校验”，不是“权限点校验”。

- 用户管理接口 `/users`、`POST /users`、`PUT /users/{id}`、`DELETE /users/{id}` 全部通过 `StpUtil.checkRole("admin")` 控制。相关代码见：`bootstrap/src/main/java/com/nageoffer/ai/ragent/user/controller/UserController.java:69-101`。
- 角色来源来自 `SaTokenStpInterfaceImpl#getRoleList(...)`，实现方式是按 `loginId` 查用户表，再返回单个角色列表。相关代码见：`bootstrap/src/main/java/com/nageoffer/ai/ragent/user/config/SaTokenStpInterfaceImpl.java:63-79`。
- 权限来源 `getPermissionList(...)` 当前直接返回空列表，说明仓库还没有落到细粒度 permission model。相关代码见：`bootstrap/src/main/java/com/nageoffer/ai/ragent/user/config/SaTokenStpInterfaceImpl.java:50-52`。

换句话说，当前实现的授权模型是：

- 默认所有业务接口都要求“已登录”
- 少数后台管理接口再额外要求“角色 = admin”
- 还没有把系统拆成 `user:add`、`knowledge:delete` 这类细粒度权限点

#### 4.5 异常与跨线程补偿

Sa-Token 抛出的认证异常，在本仓库中被统一收口：

- `NotLoginException` 被翻译为“未登录或登录已过期”
- `NotRoleException` 被翻译为“权限不足”

相关代码见：`framework/src/main/java/com/nageoffer/ai/ragent/framework/web/GlobalExceptionHandler.java:89-105`。

同时，仓库还对“非标准 Web 请求线程”做了补偿：

- `ChatQueueLimiter` 优先读 `UserContext.getUserId()`，拿不到时再回退到 `StpUtil.getLoginIdAsString()`。相关代码见：`bootstrap/src/main/java/com/nageoffer/ai/ragent/rag/service/ratelimit/ChatQueueLimiter.java:158-166`。
- MQ 消费者和定时刷新任务不会天然带着 Web 登录态，因此它们会手工注入最小化 `UserContext`。相关代码见：`bootstrap/src/main/java/com/nageoffer/ai/ragent/knowledge/mq/KnowledgeDocumentChunkConsumer.java:46-57`、`bootstrap/src/main/java/com/nageoffer/ai/ragent/knowledge/schedule/ScheduleRefreshProcessor.java:210-216`。

这说明本仓库已经明确区分了两类上下文：

- Web 请求线程：优先依赖 Sa-Token + `UserContextInterceptor`
- 异步线程 / MQ / 调度线程：需要显式补充 `UserContext`

### 5. 本仓库实现上的实践注意事项

1. `AuthServiceImpl` 目前是明文比对密码：`stored.equals(input)`。这更适合初始化或内网环境，不适合作为长期安全基线。相关代码见：`bootstrap/src/main/java/com/nageoffer/ai/ragent/user/service/impl/AuthServiceImpl.java:76-80`。
2. 如果后续要引入更细的资源授权，先补 `getPermissionList(...)`，再逐步把高价值接口从 `checkRole("admin")` 演进到 `checkPermission(...)`。官方要求角色、权限来源由 `StpInterface` 提供。[权限扩展文档](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/use/jur-auth.md)
3. 官方 FAQ 提醒：`StpInterface#getPermissionList` 在鉴权时会被频繁调用，复杂查询要考虑缓存。本仓库当前 `getRoleList(...)` 仍是实时查库实现，后续扩展权限模型时要留意性能。[官方 FAQ](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/more/common-questions.md) 相关代码见：`bootstrap/src/main/java/com/nageoffer/ai/ragent/user/config/SaTokenStpInterfaceImpl.java:63-79`。
4. 当前前端把 token 放在 `localStorage`，对后台系统很直观，但后续若要切到 Cookie 托管、刷新 token 或更严格的 XSS 防护，需要同步改造前端 header 注入与后端 `token-name` 约定。相关代码见：`frontend/src/utils/storage.ts:31-59`、`frontend/src/services/api.ts:13-25`。
5. 新增异步任务、MQ 消费者或 SSE 旁路逻辑时，不要假设 `UserContext` 一定存在；要么显式补齐 `UserContext`，要么像 `ChatQueueLimiter` 一样保留从 Sa-Token 回退读取 `loginId` 的兜底逻辑。相关代码见：`bootstrap/src/main/java/com/nageoffer/ai/ragent/rag/service/ratelimit/ChatQueueLimiter.java:158-166`。

## 原因

当前实现之所以采用“Sa-Token + UserContext”双层结构，原因很明确：

1. Sa-Token 负责认证事实本身，避免业务代码到处拼 token、解 token、判登录状态。
2. `UserContext` 负责把 `loginId` 变成业务友好的 `LoginUser`，让业务层只关心 `userId / username / role`。
3. 角色来源继续掌握在本仓库自己手里，方便以后从“单角色”演进到“多角色 / 多权限点”。
4. 异步任务不天然继承 Web 登录态，因此必须把“认证事实”和“业务快照”分层，才能在 MQ、调度、流式响应等场景下灵活补偿。

## 结论

1. Sa-Token 在本仓库里承担的是“登录态真相源”的角色：登录、登出、登录检查、角色检查都以 `StpUtil` 为核心。
2. 本仓库的业务层并不直接依赖 Sa-Token，而是依赖 `UserContext` 中的 `LoginUser` 快照，这也是 `Sa-Token 登录态` 和 `UserContext` 的真正边界。
3. 当前授权模型以“已登录 + admin 角色”两层为主，权限点体系尚未启用，因为 `getPermissionList(...)` 仍返回空列表。
4. 当前仓库已经具备在 Spring Boot 4 平台继续扩展 Sa-Token 的基础条件，但若要进一步走向生产级安全与细粒度授权，还需要补上密码安全、权限点建模与异步上下文治理。

## 后续建议

- 如果以后要把权限模型做细，优先补 `getPermissionList(...)`，再把高价值接口从角色校验迁移到权限校验。
- 如果以后要更严格的安全基线，优先替换明文密码比较，并评估 token 存储介质。
- 如果以后要在更多异步链路里复用当前用户，先统一 `UserContext` 补齐和清理策略，再考虑额外的回退逻辑。
